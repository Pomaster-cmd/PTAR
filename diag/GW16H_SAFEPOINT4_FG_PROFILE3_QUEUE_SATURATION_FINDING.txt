Historical correction
---------------------
The earlier hardware-validated B18K18 run with 9213 unique frames / 9352 output
frames was NOT 1920x1080/60. It was the historical compact B18K18 profile at
960x540/60, 5000 kbps. Its NV12 payload was 777600 bytes/frame (~44.5 MiB/s at
60 Hz) and QSV queue-full drops were zero.

Current profile 3 uses 3110400 NV12 bytes/frame, exactly 4x the raw bytes per frame
and ~178 MiB/s at 60 Hz. Therefore the old compact B18K18 result cannot be used as
evidence that the current 1080p60 consumer path has already been hardware-validated.

SAFEPOINT5 / QSVPRIORITY1 rationale
-----------------------------------
The locked B18K18 implementation deliberately ran both asynchronous recorder workers
at THREAD_PRIORITY_BELOW_NORMAL and launched FFmpeg with BELOW_NORMAL_PRIORITY_CLASS.
That policy was validated for compact 540p60, but the field result proves the
1080p60 profile 3 consumer cannot drain the 32-frame queue fast enough under the
current scheduling policy.

SAFEPOINT5 changes consumer scheduling only:
  - encode/pipe-writer thread: BELOW_NORMAL -> NORMAL;
  - FFmpeg/QSV process: BELOW_NORMAL_PRIORITY_CLASS -> NORMAL priority class by
    removing only that CreateProcess flag;
  - CREATE_NO_WINDOW retained;
  - GPU readback worker remains BELOW_NORMAL;
  - presenter and FG remain nonblocking and keep absolute priority;
  - queue size remains 32;
  - no change to timeline, conversion, bitrate, profile dimensions, QSV command,
    state guard, SAFEPOINT routing, local VS/RS, or FG algorithm.
