RC11 FIELD FINDING — INQUISITOR / GTX 960M / WINDOWS 8.1

Hardware correction:
- The RC11 Inquisitor test was performed on the GTX 960M machine, not the RTX 3080 machine.

Observed RC11 activation sequence:
1. Dedicated D3D11 FG device/context created.
2. Four full-resolution shared legacy transport slots opened.
3. NVENC ME-only API/ring initialized.
4. Isolated display device C created.
5. Four low-resolution display mailbox slots created.
6. FG presenter 1920x1080 created.
7. ME scheduler, QPC cadence, mailbox publisher and isolated display threads all started.
8. Immediately afterward Inquisitor issued another game ResizeBuffers request for 1920x1080.
9. Wrapper emitted FG_PRESENTER_RELEASE, restored the USR presenter, forwarded the game's ResizeBuffers (which failed), and immediately began rebuilding FG.
10. The log terminates during the second FG reconstruction after device C/PTAR shader initialization; the game crashed.

Interpretation:
- SHARELEGACY2 successfully passed the previous shared-resource barriers on this GTX 960M.
- The next blocker is the continuous Inquisitor ResizeBuffers behavior racing the live legacy FG runtime teardown/rebuild.
- The same 1920x1080 ResizeBuffers pattern had already been failing repeatedly before FG without destabilizing the game.

RC12 contract derived from this finding:
- Keep RC9 keyed-primary behavior as the canonical first path.
- Persist a runtime marker only when the legacy fallback actually reaches mailbox construction.
- Only when LEGACY_ACTIVE=1 and the FG scheduler is running, reject game ResizeBuffers with DXGI_ERROR_INVALID_CALL without touching resources.
- FG OFF / pre-scheduler / keyed-primary sessions use the exact original ResizeBuffers path.
- This means the SatGat keyed-primary path remains unmodified by RESIZEGUARD1.
